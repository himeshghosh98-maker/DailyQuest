# DailyQuest — Technical Project Summary

Comprehensive technical documentation and architectural analysis of the DailyQuest full-stack application as of October 2026.

---

## 1. PROJECT OVERVIEW

### Description
DailyQuest is a gamified productivity and routine tracking application that models personal habits, scheduled tasks, and focus sessions as an RPG-style quest system. Users create recurring or one-time routines, earn Experience Points (XP) proportionally based on task completion, advance through numerical adventurer levels, maintain consecutive daily streaks (governed by an 80% daily completion threshold), and unlock achievement badges. The app features a dedicated Focus Room with a multi-phase Pomodoro timer, live ambient audio chimes, historical completion analytics with GitHub-style heatmaps, a structured activity audit table, end-of-day report grading (S/A/B/C/D), AI-powered productivity summaries and suggestions, and bi-directional offline synchronization.

### Tech Stack
- **Frontend Framework**: Next.js 14.2.15 using the App Router (`src/app`), React 18.3.1, React DOM 18.3.1. (A secondary Vite 6.3.5 configuration exists in `vite.config.js` for standalone builds).
- **Backend Framework**: Express 4.21.2 running on Node.js with native ES Modules (`"type": "module"`).
- **Database & ODM**: MongoDB via Mongoose 8.9.5. In development, the backend automatically provisions a local persistent database via `mongodb-memory-server` 10.1.4 (persisted to `server/.mongo-data` using the WiredTiger storage engine) when no external connection string is provided.
- **Authentication**: Stateless JSON Web Tokens (`jsonwebtoken` 9.0.2) signed with HS256 and salted password hashing via `bcrypt` 5.1.1 (10 salt rounds). Transmitted via the `Authorization: Bearer <token>` HTTP header. Also features a local-only Guest Exploration mode that operates without server credentials.
- **Hosting / Dev Setup**:
  - Web client: `http://localhost:3000` via Next.js development server (`npm run dev`).
  - API server: `http://localhost:4000/api/v1` via Node.js file-watching (`npm --prefix server run dev`).
  - Concurrent launcher: `npm run dev:all` using `concurrently` 10.0.5.

### Database Models & Schemas

#### 1. `User` (`server/src/models/User.js`)
- `name`: `String` (Required, trimmed, max 30 chars) — Display name.
- `nameKey`: `String` (Required, unique, indexed) — Lowercased name for case-insensitive uniqueness.
- `passwordHash`: `String` (Required, hidden via `select: false`) — Bcrypt salt hash.
- `createdAt`, `updatedAt`: `Date` — Managed via Mongoose timestamps.

#### 2. `State` (`server/src/models/State.js`)
- `user`: `ObjectId` (Ref: `User`, required, unique) — 1-to-1 relationship per user.
- `version`: `Number` (Default: 1) — Data migration schema version.
- `tasks`: `Mixed` (Default: `[]`) — Normalized array of active user tasks.
- `totalXp`: `Number` (Default: 0) — Cumulative lifetime XP.
- `history`: `Mixed` (Default: `[]`) — Daily completed history archives.
- `focusSessions`: `Mixed` (Default: `[]`) — Logged focus session records.
- `focus`: `Mixed` (Default: `null`) — Active ongoing focus session state.
- `badges`: `Mixed` (Default: `{}`) — Map of `{ [badgeId]: unlockIsoDate }`.
- `settings`: `Mixed` (Default: `{}`) — User preferences (theme, audio, intervals).
- `lastActiveDate`: `String` (Default: `""`) — YYYY-MM-DD tracking string.
- `migratedAt`: `Date` (Default: `null`) — Timestamp of initial client localStorage sync.
- `createdAt`, `updatedAt`: `Date` — Managed via Mongoose timestamps.

#### 3. `AiCache` (`server/src/models/AiCache.js`)
- `key`: `String` (Required, unique) — Cache slot identifier (`${userId}:${kind}`).
- `user`: `ObjectId` (Required, indexed) — Reference to requesting user.
- `kind`: `String` (Required) — `'insights'`, `'weekly-summary'`, or `'suggest-tasks'`.
- `source`: `String` (Enum: `['claude', 'rules']`, required) — Provenance of the payload.
- `payload`: `Mixed` (Required) — The cached response data.
- `expiresAt`: `Date` (Required) — TTL index (`expireAfterSeconds: 0`) for automatic MongoDB eviction.

### Middleware

#### In Use
1. `cors`: Dynamic origin validation allowing configured origins and non-production localhost ports (`3000`, `3001`, `5173`).
2. `express.json`: Body parser with a `2mb` payload size limit.
3. `requireAuth` (`server/src/middleware/auth.js`): Verifies the JWT Bearer token and assigns `req.user = { id, name }`.
4. `validate` (`server/src/middleware/validate.js`): Zod schema validator for `req.body`, `req.query`, and `req.params`. Strips unknown keys and reassigns sanitized values.
5. `notFound` (`server/src/middleware/notFound.js`): 404 handler that produces `ApiError.notFound()`.
6. `errorHandler` (`server/src/middleware/errorHandler.js`): Centralized error formatter. Converts Zod errors, Mongoose duplicate key errors (code 11000 -> 409 `CONFLICT`), and CastErrors into standardized JSON: `{ message, code, details? }`.

#### Not Implemented Yet
- **Rate Limiting**: No rate-limiting middleware (e.g. `express-rate-limit`) is installed; `/api/v1/auth` and `/api/v1/ai` endpoints have no throttling.
- **Request Logging**: No structured logger (e.g. `pino-http` or `morgan`) is active; requests are not logged to stdout.
- **Security Headers**: No `helmet` middleware is mounted (only `app.disable('x-powered-by')` is present).

### AI Provider Integration

- **Service**: Anthropic Messages API (`https://api.anthropic.com/v1/messages`).
- **Model**: `claude-sonnet-4-5` (overridable via `CLAUDE_MODEL`).
- **Credential Storage**: Read strictly on the server from `CLAUDE_API_KEY` or `ANTHROPIC_API_KEY`.
- **Request Timeout**: Configured with a 30-second `AbortSignal.timeout(30_000)`.
- **Deterministic Rule-Based Fallback**:
  - If `CLAUDE_API_KEY` is not provided, or if Anthropic API returns a non-200 code or times out, the backend executes internal rule-based algorithms (`generateRuleInsights`, `generateRuleSummary`, `generateRuleSuggestions`).
  - These inspect user history, compute rolling completion rates, detect missed habits, and generate structured suggestions without failure.
  - Results are tagged with `source: 'rules'` and cached in `AiCache` for the configured cache duration.

### Frontend-to-Backend Communication

- **API Client**: Implemented in `src/api/client.js` with base URL resolving from `NEXT_PUBLIC_API_URL` (defaults to `http://localhost:4000/api/v1`).
- **Token Storage**: JWT tokens are stored in `localStorage` under `dailyquest:auth` and mirrored in the `dailyquest_auth` cookie for routing synchronization.
- **Token Header**: Sent as `Authorization: Bearer <token>` on all requests when the user is not in guest mode.
- **Offline Sync & Storage (`src/storage.js`)**:
  - `localStorage` under `dailyquest:v1` serves as the immediate read/write cache.
  - State changes are debounced (700ms delay) and flushed to the backend via `PUT /api/v1/state`.
  - Failed network requests are queued in `localStorage` under `dailyquest:pending` and synced when `window.addEventListener('online')` triggers.
  - Background state refresh dispatches custom window event `'dailyquest:server-state'`.

### State Management Approach

- **Architecture**: React Context API with modular custom providers:
  - `AuthContext` (`useAuth`): Handles user identity, login, signup, guest sessions, logout, and client route guards.
  - `QuestContext` (`useQuest`): Main centralized state reducer managing tasks, XP calculation, daily history entries, focus sessions, badges, settings, and task timers.
  - `FocusContext` (`useFocus`): Focus room timer engine managing countdown intervals, active task linkage, and background ticks.
  - `ModalContext` (`useModals`): Controls modal states (New Quest, Edit Quest, Finish Day Report, Confirm Dialog).

## 6. KNOWN GAPS OR RISKS

Factual list of items identified in the codebase that are unhandled, incomplete, or present technical risks:

1. **Absence of Frontend Tests**: The `src/` directory contains zero automated unit, integration, or end-to-end tests (no Jest, Vitest, or Playwright setup).
2. **Missing Backend Rate Limiting**: The Express server does not implement rate limiting on authentication routes (`/api/v1/auth/login`, `/signup`) or AI routes (`/api/v1/ai/*`), leaving them vulnerable to credential brute-forcing or API quota exhaustion.
3. **Absence of Security Headers**: Express security headers via `helmet` (CSP, HSTS, X-Content-Type-Options) are not configured.
4. **No Password Recovery**: The authentication system has no password reset, email recovery, or forgotten passcode flow; users who lose credentials cannot recover accounts.
5. **No Email Verification**: User signups do not collect or verify email addresses; uniqueness is enforced solely by username.
6. **Loose Database Schema for Game State**: In `server/src/models/State.js`, tasks, history, focus sessions, and badges are typed as `mongoose.Schema.Types.Mixed`, bypassing database-level type constraints in favor of client offline compatibility.
7. **Potential Last-Write-Wins Race Condition**: Full state updates use `PUT /api/v1/state` with entire document replacement; concurrent edits across two devices could lead to the last save overwriting the other device's changes.
8. **Browser Autoplay Audio Policy**: Focus room victory chimes rely on Web Audio API `AudioContext`, which can be blocked by browser autoplay restrictions if triggered before user interaction on that page.
9. **Dual Build Systems Present**: The codebase contains both Next.js App Router (`next.config.mjs`) and legacy Vite (`vite.config.js`, `index.html`) configurations, which may cause developer confusion if scripts are run interchangeably.
10. **Client-Side Auth Hydration Flash**: Initial page renders display an unauthenticated state for a few milliseconds while `localStorage` is read on client mount, before hydrating the user session.
